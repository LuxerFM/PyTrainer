# Архітектура PyTrainer

Документ для того, хто читає код: як розкладені шари, чому саме так і де
додавати нові можливості.

## Три шари

```
curriculum/        ЩО вчити            — дані, які не знають про інтерфейс
    month*.py        задачі: умова, заготовка, перевірки, підказки
    drills1.py       дрили: 5–12-хвилинна практика після кожного тижня місяця 1
    cheatsheets.py   шпаргалки та автопідбір за темою задачі
trainer/core/      ЯК перевіряти       — правила навчання, база, запуск коду
    errors.py        traceback → людське пояснення (що це і що робити)
    exec_runner.py   режим --exec-runner: .exe виконує чужий файл сам собою
    selfcheck.py     режим --self-test: чи справді приходить вердикт
    runner.py        запуск коду в окремому процесі + перевірки
    review.py        холодне повторення: яку здану задачу дістати з пам'яті
    codereview.py    розбір коду: правила над ast → людські зауваження
    mistakes.py      журнал помилок: що ще «висить», а що закрито — і чим саме
    digest.py        тижневий огляд: сім днів навчання в числах і вердикті
trainer/ui/        ЯК показати         — Qt-віджети й тема
trainer/cli.py     вибір режиму запуску (прапорці розбираються до імпорту Qt)
```

Залежності йдуть лише в один бік: `ui → core → curriculum`. Ядро не імпортує
жодного модуля PySide6, тому його можна запускати й тестувати без екрана
(саме так і роблять тести: `QT_QPA_PLATFORM=offscreen`).

## Потік однієї спроби

```
користувач натискає F5
      │
      ▼
ui/main_window.py ──► core/runner.run_task(task, code)
      │                     │ окремий процес у тимчасовій папці (Python, а в .exe —
      │                     │ сам .exe з --exec-runner: іншого Python там немає)
      │                     │ таймаут 5 с, ліміт виводу 64 КБ, фікстура stdin
      │                     ▼
      │              RunResult(stdout, stderr, checks)
      ▼
core/session.StudySession.record_result(task, result)
      │  вирішує: скільки XP, здано чи ні, у чергу повторень чи ні
      ▼
core/db.Database ──► SQLite (progress / attempts / reviews)
      │
      ▼
ui оновлює дерево, панель тестів, XP, стрік і пише Python-Roadmap.md + progress.json
```

Ключове: **правила навчання не живуть в інтерфейсі**. `StudyUpdate`, який
повертає сесія, містить усе, що потрібно намалювати (`xp`, `passed`,
`review_days`, `mastered`, `notes`). Тому ці правила перевіряються
юніт-тестами у `tests/test_session.py` без жодного вікна.

## Холодне повторення: згадка замість упізнавання

Звичайне повторення відкриває задачу так, як її було здано: із твоїм кодом у
редакторі й підказками під рукою. Це перевіряє радше пам'ять «де що лежить»,
ніж уміння розв'язати. Тому є окремий режим, який прибирає опору:

```
ui/review_page.py  «Холодне повторення» (або Ctrl+Shift+R)
      │
      ▼
core/review.pick_cold_task(db, exclude=поточна задача)
      │  лише ЗДАНІ задачі; спершу ті, що вже просять повторення,
      │  а якщо черга порожня — випадкова зі зданих
      ▼
ui/main_window.start_cold_review()
      │  редактор із заготовки, panel.set_locked(True) — підказки й розв'язок
      │  недоступні, зворотний відлік cold_seconds() = 3–10 хв
      ▼
F5 → core/session.record_result(..., review_mode=True)
      │  успіх: інтервал 1/3/7/30 іде далі + бонус XP;
      │  інтервал аж ніяк не зменшується — задача зникає з черги
      │  провал: задача повертається в чергу (наступна спроба завтра)
      ▼
режим вимикається сам: у наступній спробі підказки вже доступні
```

Три деталі, які легко зламати й важко помітити:

- **збережений код не затирається.** У холодному повторенні редактор починає
  із заготовки, і саме тому `_start_run` та `_tick` не пишуть його в базу:
  інакше твій справжній розв'язок замінився б на заготовку, а автозбереження
  зробило б це автоматично й непомітно;
- **рахується лише одна спроба.** Після вердикту режим вимикається: якщо не
  згадав — далі можна спокійно пройти задачу з підказками, а не залипати в
  холодному режимі до півночі;
- **утримана задача лишається утриманою.** Успішне холодне згадування задачі,
  яка вже пройшла всі чотири інтервали, не повертає її в чергу — воно дає
  найщедріший бонус XP і нічого не ламає (див. `session._handle_success`).

## Рев'ю коду: читач замість компілятора

Тести перевіряють, чи код працює. Розбір коду (вкладка «Рев'ю», `F6`)
перевіряє інше: чи його зрозуміє людина. Це той самий поділ, що між
`runner.py` і `codereview.py` — перший виконує код, другий його читає.

```
ui/task_panel.py  вкладка «Рев'ю»: картки зауважень + кнопка «Рядок N»
      │  F6 або кнопка «Розібрати код»; після кожного запуску — тихо сам
      ▼
core/codereview.review_code(code, keep=…)
      │  ast.parse → правила RULES → Remark(kind, title, advice, line)
      │  keep — імена, які читають приховані перевірки задачі
      ▼
CodeReview(remarks, summary) ─► картки в панелі, • заголовок «Рев'ю · N»
```

Рішення, які легко зламати:

- **розбір не має ламатися на коді користувача.** Код, який не компілюється,
  повертає один рядок «спершу виправ синтаксис»; кожне правило викликається
  в `try`, щоб одна помилка в правилі не вбила весь розбір;
- **`keep` — це не ввічливість, а правда.** Перевірки виконуються в тому ж
  файлі, тому можуть читати змінні людини (`BASE_URL` у мережевих задачах).
  Без цього списку розбір радив би видалити те, без чого задача не здасться;
- **ліміт на шість карток.** Шість виправлень — це вечір роботи; двадцять
  нарікань не читає ніхто. У підсумку видно, скільки їх усього;
- **`elif` — не новий поверх.** В `ast` гілка `else` — це список операторів, а
  `elif` — той самий `if` усередині `orelse`, тому калькулятор з шістьма
  `elif` виглядав би як шість рівнів вкладеності;
- **заготовку не розбираємо.** Її писав не учень, і «невикористані змінні» в
  ній — не його помилка.

Правила живуть у `RULES` — список функцій `(tree, keep) → list[Remark]`.
Додати своє: дописати функцію з докладним рядком документації й додати її в
`RULES`. Нема докладної перевірки — нема зауваження.

## Тижневий огляд: мета-погляд раз на тиждень

Щоденний план відповідає на питання «що робити сьогодні». Тижневий огляд
(`digest.py`) — на питання «і що з цього вийшло?». Без нього навчання
перетворюється на стрічку справ: задачі здаються, помилки накопичуються, а чи
стало легше — не видно нізвідки.

```
db.attempts_between(start, end) ─┐
db.solved_between(start, end)   ─┤
db.task_results()               ─┼─► core/digest.weekly_digest(db, today) ─► WeeklyDigest
db.due_reviews(last)            ─┤        несвідомий про Qt: тіль/вердикт/markdown
db.streak(), db.total_xp()      ─┘                    │
                                                     ├─► ui/stats_page: рядок + кнопка
                                                     ├─► ui/digest_page.DigestDialog (Ctrl+Shift+W)
                                                     └─► ui/main_window.save_report → markdown-файл
```

Окремо — журнал помилок (`mistakes.py`). Він класифікує кожну помилку за
**подвійним критерієм**: чи був після неї успіх і чи був цей успіх чистим.

```
mistake_history() ─► task_id + error_kind ─► дивимось на attempts:
     є успіх після помилки?  ── ні  ──────────────────► ВІДКРИТО
               │ так
     він із підказкою/розв'язком? ── так ─────────────► ЗАКРИТО З ДОПОМОГОЮ
               │ ні
     здано чистим проходом ──────────────────────────► ЗАКРИТО
```

Рішення, які легко зламати:

- **порівнюємо за `id` спроби, а не за часом.** `created_at` має точність до
  секунди, і дві спроби в одну секунду мали б однаковий час — порядок тоді
  вгадувати неможливо. Запит `mistake_history` віддає і `pass_id`, і
  `last_id`, і сортує з `m.last_id` як другим ключем;
- **чистим проходом вважається прохід без підказок і без розв'язку.** Для
  старих баз (схема не знала колонки `clean`) є запасний шлях: якщо задача
  здана й жодної підказки не відкривано — закрито. Схема має міні-міграцію,
  тому база не ламається;
- **три стани, а не два.** Вважати «закрито» будь-яке здавання означає, що
  найкорисніший список у тренажері стає історією страждань; вважати закритим
  лише чисте здавання — що старий `NameError` висить вічно. «Закрито з
  допомогою» дає середину і веде в холодне повторення;
- **вердикт рахується з тих самих даних, що й числа.** `WeeklyDigest.verdict`
  — властивість, а не окрема функція, тому «порожній тиждень», «рваний
  тиждень» і «закрито чисто» не можуть суперечити карткам поруч;
- **звіт живе і після тижня.** `as_markdown()` друкує нерухомий знімок: через
  місяць цифри в тренажері вже інші, а перечитати, як пройшов тиждень,
  корисно — тому в тексті стоїть дата створення.

## Два рівні вправ: задачі й дрили

У плані навмисно співіснують дві різні за розміром одиниці роботи.

| | Задача | Дрил |
|---|---|---|
| Скільки часу | 10–25 хв | 5–12 хв |
| Скільки навичок | одна-дві, часто з новою теорією | рівно одна, вже знайома |
| Скільки перевірок | 3–7, буває `stdout` і `code` | 2–4, зазвичай на **різних входах** |

Дрили з'явилися після чесного підрахунку: 18 задач місяця 1 — це 230 хвилин,
тобто кілька вечорів на місяць «бази». Дрил розв'язує це інакше, ніж просто
додати ще задач: він настільки короткий, що його не страшно почати, і його
перевірки спеціально складені так, щоб **вписати відповідь руками не вийшло**
(три різні входи для суми цифр, три набори чисел для максимуму, три різні
слова для голосних).

Тема дрилів стоїть у плані одразу після свого тижня — тому `plan.py`
природно веде до тренування, поки навичка ще гаряча, а статистика по цій темі
окремо показує, що саме кульгає.

## Модель даних плану

```python
Month(title, subtitle, topics=[Topic(title, tasks=[Task, ...])])

Task(id, title, statement, starter, level, checks, hints,
     stdin, files, entrypoint, minutes, stub,
     source, source_url, cheatsheet)
```

- `checks` — список `Check`: або `code` (assert-код після коду користувача),
  або `stdout_*` (що програма надрукувала при заданому вводі).
- `hints` — підказки; остання з `solution=True` відкривається за таймером.
- `files` — додаткові файли проєкту (наприклад `utils.py`), які з'являться
  поруч із розв'язком у тимчасовій папці.
- `stub=True` — пункт плану, який робиться поза тренажером (venv, Git, pytest);
  його можна позначити галочкою вручну.
- `source` / `source_url` — звідки задача (LeetCode, Codewars). Задача показує
  це в умові, а перевірки завжди написані свої.
- `cheatsheet` — ключ міні-довідки з `curriculum/cheatsheets.py`. Порожній —
  шпаргалка підбирається за словами в назві теми й задачі.

## Інформаційний шар у панелі задачі

Права панель має шість вкладок, і кожна відповідає за своє питання новачка:

| Вкладка | Питання, на яке відповідає |
|---|---|
| Задача | «Що від мене хочуть?» — умова, тема, номер задачі, оцінка часу |
| Тести | «Що саме перевірять і що вийшло?» — список перевірок до запуску, результат після |
| Рев'ю | «Чи зрозуміє це інша людина?» — розбір коду через `ast` |
| Довідка | «Як це пишеться?» — шпаргалка, підібрана під тему |
| Підказки | «Куди дивитись?» — три рівні, розв'язок за таймером |
| Історія | «Як я рухаюсь?» — усі запуски, XP, час над задачею |

Пояснення помилок — окремий шар, а не частина інтерфейсу: `core/errors.py`
розбирає traceback (або короткий рядок із прихованої перевірки) і повертає
`Explanation(kind, message, meaning, advice, line, source)`. Це означає, що
той самий модуль можна використати в CLI чи вебверсії без жодних змін.

Конструктори `task()`, `code()`, `stdout()`, `hint()`, `solution()` роблять
файли-дані читабельними: задача описується майже як текст.

## Таблиці SQLite

| Таблиця | Призначення |
|---|---|
| `progress` | стан задачі: `status`, `best_xp`, `bonus_xp`, `hints_used`, `solution_used`, `active_seconds`, збережений код |
| `attempts` | кожен запуск: час, вердикт, чи це була перевірка і чи був прохід чистим (`clean`). Звідси стрік, календар, журнал помилок і тижневий огляд |
| `reviews` | черга повторень: `due_date`, `interval_index` |

Схема має міні-міграції (`Database._migrate`), тому база, створена старішою
версією, не ламається — нові колонки додаються на місці.

## Правила навчання (усе в `core/scoring.py` і `core/session.py`)

| Правило | Формула |
|---|---|
| XP за задачу | база рівня × (1 − 15% за кожну підказку), не нижче 40% |
| Вставлений розв'язок | рахується як 3 підказки + обов'язкове повторення |
| Повторний прохід | 30% базового XP (додається до `best_xp`, якщо більший) |
| XP за повторення | 20/40/60/80% бази залежно від глибини інтервалу |
| Інтервали | 1 → 3 → 7 → 30 днів; п'яте успішне повторення знімає з черги |
| Утримано | задача здана і більше не має запланованого повторення |
| Стрік | дні поспіль із хоч одним запуском коду (сьогодення не обов'язкове до вечора) |
| Холодне повторення | підказки й розв'язок вимкнено, час обмежено; вердикт веде інтервал далі, а утриману задачу не повертає в чергу |
| Закриття помилки | тільки чистий прохід після неї; здано з підказкою — «закрито з допомогою» |

## Шляхи, дані й зібраний .exe

Найпідступніша різниця між запуском із коду й запуском зі збірки — де
шукати файли. `trainer/paths.py` вирішує це трьома функціями:

| Функція | Звичайний запуск | Зібраний `.exe` |
|---|---|---|
| `app_folder()` | корінь проєкту | тека, де лежить сам `.exe` |
| `resource(*parts)` | корінь проєкту | тека розпакування `sys._MEIPASS` |
| `is_frozen()` | `False` | `True` |

Ризик тут не косметичний: `--onefile` розпаковує програму в тимчасову теку
й прибирає її після виходу, тому база з прогресом і `Python-Roadmap.md`, що
лежали б **усередині**, зникали б після кожного закриття вікна. Саме тому
все, що належить людині, живе поруч із `.exe`:

```
PyTrainer.exe
pytrainer.db      прогрес
progress.json     він же у читабельному вигляді
pytrainer.ini     тема, масштаб тексту, розкладка вікна
Python-Roadmap.md генерований план
backups/          тихі копії бази (7 останніх)
```

Перед кожним запуском робиться копія бази (`db.backup_database`) через
`sqlite3.Connection.backup` — копіювання файлу наосліп може застати базу
посеред запису.

Збірка: `tools/build_exe.py` + `pytrainer.spec`. Специфікація викидає
невикористані модулі Qt (їх у PySide6 більшість) і англійські переклади Qt —
без цього однофайловий `.exe` важить у кілька разів більше. Зате вона
**додає** модулі, потрібні не тренажеру, а коду задач (`csv`, `datetime`,
`sqlite3`, `urllib`…): PyInstaller збирає лише те, що знайшов у коді, тому без
явного списку `import csv` у розв'язку падав би **тільки** в `.exe`.

CI збирає `.exe` на кожен push і робить із ним дві різні перевірки:
`--demo --screenshot` відповідає на питання «чи відкривається вікно», а
`--self-test` — на питання «чи приходить вердикт». Це різні питання, і перше
буває «так» тоді, коли друге — «ні».

Тег `v*` додає архів у реліз.

## Коли .exe запускає код користувача

Найнебезпечніша різниця між запуском із коду й зі збірки лежить не у шляхах,
а в `sys.executable`. Звичний `python` — це інтерпретатор; зібраний `.exe` —
це програма, у якій інтерпретатор захований усередині. Тому `interpreter_command()`
у `core/runner.py` будує команду з двох варіантів:

| | Запуск із коду | Зібраний `.exe` |
|---|---|---|
| Команда | `python -X utf8 -u solution.py` | `PyTrainer.exe --exec-runner solution.py` |
| Прапорці | розуміє інтерпретатор | прапорці інтерпретатора не потрібні: вони вже в env |
| Хто виконує файл | сам Python | `exec_runner.main()` у тому ж процесі |

Що сталося б без цієї різниці (і сталося насправді): `PyTrainer.exe -X utf8 -u
solution.py` — це запуск **другого вікна** тренажера. Bootloader ігнорує невідомі
прапорці, тому код користувача не виконувався взагалі, вердикт не приходив,
таймаут вбивав лише bootloader, а його нащадок жив далі, тримав відкритими
`__stdout.txt` і `__stderr.txt` — звідси WinError 32 під час прибирання тимчасової
теки. Три речі лагодили це окремо, і кожна потрібна:

- `--exec-runner` — щоб файл виконувався, а не відкривалося друге вікно;
- `_terminate_tree()` — `process.kill()` зупиняє лише безпосередню дитину,
  а в `.exe` справжній інтерпретатор — дитина bootloader-а;
- `_remove_dir()` — прибирання теки не варте жодного результату перевірки,
  тому воно має право не вдатись, а не зірвати запуск.

Помилку в коді користувача `exec_runner` друкує **сам**, а не віддає назовні:
у віконному `.exe` необроблений виняток перетворюється на діалог із кнопкою
«ОК», тобто звичайна помилка виглядала б як таймаут.

Знімки для README робить `tools/make_screenshots.py`: він піднімає вікно на
демо-базі, чекає на справжній результат перевірок і зберігає `window.grab()`.
Тому картинки в README — це рендер застосунку, а не макет.

## Шрифти й текст

У панелі задачі навмисно **два шрифти**: проза (умова, пояснення, довідка) і
моноширинний (код). `theme.prose_family()` і `theme.mono_family()` повертають
перший доступний шрифт системи і кешують результат; `_wrap_html()` підставляє
його у HTML для `QTextBrowser`.

Підказки й шпаргалки зберігаються **звичайним текстом**, а не HTML:
`task_panel.plain_to_html()` сам вирішує, які рядки схожі на код (рядки
`def`, `print(`, присвоєння), і збирає їх у `<pre>`. Тому текст у даних
лишається читабельним, а вигляд — охайним.

Дві пастки Qt, на які вже наступили:

- `line-height` у `QTextDocument` працює лише у **відсотках** (120% дає ~21px
  на рядок при 14px); `line-height: 1.2` дає несподіваний результат;
- QSS `objectName` змінюється без перемальовування — після зміни потрібен
  `style().unpolish()/polish()` (див. `TaskPanel._repolish`).

## Свідомі обмеження

- Код користувача виконується з правами його користувача: це тренажер для
  власного навчання, а не пісочниця для чужого коду.
- Одна задача = один файл-відповідь (`entrypoint`) плюс незмінні допоміжні
  файли; редагування кількох файлів у редакторі поки не підтримується.
- Мережеві задачі працюють не зі справжнім інтернетом, а з локальною
  фікстурою зі стандартної бібліотеки (`curriculum/fixtures.py`). Так задача
  перевіряється однаково в тестах і в CI, не залежить від чужих API й не
  потребує `requests`. Навички ті самі: статус-коди, JSON, авторизація.
